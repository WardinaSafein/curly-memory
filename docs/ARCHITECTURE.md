# CyberWR: Architecture

CyberWR is a 2D illustrated, story-driven cybersecurity adventure for adults (corporate employees, 18+).
It is **click-to-explore**: illustrated locations, hotspots, dialogue, interactions and cinematic camera
work, not a movement-heavy RPG. It runs in the browser and targets desktop first.

This document covers the code. For art deliveries see [ASSET_SPEC.md](ASSET_SPEC.md), and for the
asset manifest format see [ASSET_MANIFEST.md](ASSET_MANIFEST.md).

---

## 1. Stack

| Layer | Choice | Notes |
|---|---|---|
| Engine | **Phaser 4** (4.2.x) + **TypeScript** | WebGL renderer, scenes, tweens, cameras, filters (glow), input |
| Build / dev server | **Vite** | Hot reload; `.ink` story files compile at import time through a small plugin |
| Narrative | **Ink** (`inkjs`) | Writers edit `src/content/story/*.ink` as plain text |
| Asset pipeline | Node + `sharp` (`tools/`) | Validates deliveries, generates placeholders, trims, writes the runtime manifest |
| Tests | **Vitest** (logic), Playwright smoke test (`npm run smoke`) | |
| Saves | `localStorage` behind a `SaveService` interface | A backend can replace it later |
| Backend | *Not in the prototype* | Planned: accounts, cloud saves, progress, server-side answer checks |

## 2. Repository layout

```

  core/                   engine-agnostic services

    SaveService.ts          LocalSaveService / MemorySaveService

  systems/                reusable engines (no story content inside)
    rig/                    cutout rig: definition, skeleton (FK), animation, Phaser renderer
    scene/                  location data model (SceneDef, hotspots, actions)
    dialogue/               Ink runner + dialogue box UI
    cinematics/             beat-based cinematic director
    fx/                     PerspectiveLid (3D laptop lid)
  content/                game-specific data
    assets/manifest.json    every asset the game expects (the contract with the art team)
    characters/             player.rig.json, player.anims.json, player factory
    scenes/                 bedroom.ts, cybertown.ts (pure data)
    story/prototype.ink     dialogue
    cinematics/portal/      one file per beat of the laptop portal cinematic
  scenes/                 Phaser scenes: Boot, Preload, Title, Explore, Cinematic, RigLab
  ui/                     Button, layout anchors
tools/                    build-assets, make-rig-template, smoke test, SVG helpers
tests/                    Vitest unit tests
assets-src/               raw art deliveries (the art team's drop zone)
public/assets/            GENERATED by `npm run assets` (git-ignored)
docs/                     this file, asset spec, manifest format, rig template package
```

**Rule of thumb:** `systems/` holds no story content and `content/` holds no engine logic. A new
location, dialogue or cinematic beat should only need changes in `content/`.

## 3. Runtime flow

```
Boot ──▶ Preload ──▶ Title ──▶ Explore(bedroom) ──[laptop hotspot]──▶ Cinematic(portal) ──▶ Explore(cybertown, entry "portal")
 │          │          │
 │          │          └─ review menu: Rig Lab · Bedroom · Portal · CyberTown · Reset save
 │          └─ loads every asset in the runtime manifest (progress bar)
 └─ loads public/assets/manifest.json
```

Deep links for review: `?scene=title|riglab|bedroom|cybertown|portal`, `&entry=portal`,
`&nosave` (in-memory save), `&reset` (wipe the save).

## 4. Systems

### 4.1 Assets: manifest-driven, placeholder-first

Game code only ever uses **asset keys** (`town.bldg.03`, `player.eyes.e01.closed`). The declared
manifest (`src/content/assets/manifest.json`) lists every key with its file, exact size and rules.
`npm run assets` then:

1. expands templates (`{n}` variables, rig part sets) into concrete assets;
2. validates each delivered PNG in `assets-src/` (format, size, transparency, edge padding, halos,
   green-screen spill and, for rig parts, alignment with the template);
3. generates a **labelled placeholder** for anything missing or invalid, so the game always runs;
4. trims transparent borders where requested and records the offsets;
5. writes `public/assets/` + the runtime manifest + `_reports/` (asset report, rig composite).

So real art "drops in": put a correctly named file in `assets-src/`, run `npm run assets` (it
also runs automatically before `npm run dev` and `npm run build`), and reload. Full format:
[ASSET_MANIFEST.md](ASSET_MANIFEST.md).

### 4.2 Characters: cutout rig

Characters are **layered parts animated in code**, not frame-by-frame sprite sheets. This keeps
customisation affordable (swap a hairstyle part instead of redrawing every frame) and keeps
AI-generated art consistent between frames.

- **`player.rig.json`** is the single source of truth: bones (joint pivots on the shared
  1024×1536 canvas), slots (one per part, in draw order), part file templates and guide shapes.
  The rig template PNGs, the placeholders and the runtime skeleton are all generated from it.
  Rig **v1.1** is fitted to the approved character design (`docs/rig-template/design_reference.png`).
- **`Skeleton`**: forward kinematics; each bone has a rest offset from its parent plus animated
  rotation / translation / scale.
- **`restPose`** (in the rig): a code-side correction applied under every animation. v1.1 relaxes the
  design's wide-set arms by ~8° so the art can be drawn exactly as designed.
- **Coverage probes**: points ~20 px past each joint (capsule ends plus explicit `mustCover`
  points) that every delivered part must paint. They are drawn as ◆ in the template and enforced
  by the validator, which turns "paint the hidden overlap" into a pass/fail check.
- **`contacts`** (foot sole points) let `npm run rig:fit-walk -- --write` recompute the walk's pelvis
  bob and the stride-matched walk speed whenever the leg joints change.
- **`Animation` / `RigAnimator`**: keyframe clips (`player.anims.json`) evaluated on three
  layers: `base` (idle/walk, cross-faded), `face` (blink), `overlay` (additive reactions such
  as surprise). Slot keys swap part states (eyes open/half/closed/wide, mouth shapes).
- **`BlinkController`**: random 2.2–5.6 s blinks with occasional double-blinks, suppressed during
  reactions.
- **`CutoutRig`** (Phaser container): one flat image per slot, so draw order is independent of the
  bone hierarchy. Its origin is the ground point between the feet. It supports facing
  left/right (mirroring), per-scene lighting tint and a bone debug overlay.
- **Walk speed** is derived from the clip's stride (`walkSpeed` in the rig), and a unit test checks
  that the planted foot stays on the ground for the whole cycle.

Animations in the rig test: **idle, blink, walk, surprise**. Everything else (talk, wave, typing,
other expressions) waits until the rig test is approved.

**Rig Lab** (`?scene=riglab`) is the review tool for rig deliveries. It provides:

- animation buttons and 0.25×/0.5×/1× speed;
- overlays of the template, the approved design and the artist's reference render;
- bone view and face zoom;
- lighting presets (desk lamp, town dusk) and backdrops;
- an in-game-size preview that really walks, so foot sliding is visible;
- a delivered-vs-placeholder checklist.

### 4.3 Locations: data-driven click-to-explore

Every location is a `SceneDef` (`src/content/scenes/*.ts`) rendered by one generic `ExploreScene`:

- **Layers**: images by asset key with parallax (`scroll factor`), depth, origin, optional
  horizontal repeat for seamless tiles and gentle "bob" motion.
- **Walk line**: click/tap the ground to walk; the camera follows in wide scenes.
- **Hotspots**: rectangle or polygon areas, a hover tooltip, an optional glow on a named layer,
  `walkTo` + `face`, then a list of **actions**.
- **Actions**: `dialogue`, `cinematic`, `goto`, `setFlag`, `anim`, `land`, `walkTo`, `camera`,
  `wait`. Every action and hotspot accepts `if` / `unless` flag guards.
- **Entries**: named spawn points with arrival actions (e.g. `cybertown#portal` drops the player
  in, then plays the arrival dialogue once).

Adding a location means adding a data file and registering it in `src/content/scenes/index.ts`.
A unit test validates every scene's asset keys, dialogue knots and targets.

### 4.4 Dialogue: Ink

- Story text lives in `src/content/story/*.ink`.
- Conventions: `Gus: line` sets the speaker, and `PLAYER: line` uses the player's chosen name.
  Tags such as `# anim: surprise` are forwarded to the scene (the explore scene plays the clip on
  the player).
- `getFlag` / `setFlag` are bound as Ink external functions, so story choices and game state stay
  in sync.
- `DialogueBox` provides a speaker plate, a typewriter (speed in settings), click/tap/Space/Enter
  to advance and 1–9 for choices. While it's open it blocks scene input.

### 4.5 Cinematics: modular beats

A cinematic is an ordered list of **beats**; each beat is a small async module that builds its own
visuals on a shared stage and passes objects to later beats through a `store`. The laptop portal
sequence is split into six beats:

```
src/content/cinematics/portal/
  laptopOpen.ts      desk close-up; lid swings open in 3D (PerspectiveLid)
  bootScreen.ts      boot logo -> wallpaper; screen light spills onto the desk
  mysteryMessage.ts  message window + Ink dialogue (ACCEPT)
  screenGlitch.ts    glitch bars, shake, glyphs leaking out (flicker < 3 Hz)
  portalPull.ts      portal rings open; camera is pulled into the screen
  dataTunnel.ts      data tunnel with the player's OWN customised rig tumbling through
  index.ts           the beat order + what happens after (goto cybertown#portal)
```

Beats can be reordered, replaced (e.g. by a hand-animated version) or reused without touching
each other. The `CinematicDirector` routes every wait, tween and dialogue, so **Skip** (button or
Esc) works for all beats automatically. Waits resolve, tweens jump to their end state and
choices take their first option.

**The player's customised character after the portal.** Cinematic art never contains the player.
The tunnel and the CyberTown landing composite the live rig with the saved appearance.

**PerspectiveLid.** Phaser 4 removed `Mesh`/`Plane`, so the lid is a flat image cut into 64
strips, each projected through a simple pinhole camera (15° elevation). The art is drawn flat and
front-on, and the code supplies the 3D.

### 4.6 State, saves and settings

`GameState` holds the player name, appearance, story flags, current scene and settings (text
speed, reduced motion, volume). Every change persists through `SaveService` (`localStorage` now).
A backend implementation of the same interface will add cloud saves without touching game code.

### 4.7 Desktop first, responsive- and touch-ready

- A fixed 1920×1080 logical canvas, scaled to fit (`Phaser.Scale.FIT`).
- UI is placed through `src/ui/layout.ts` anchors, not hard-coded screen positions. Moving to an
  `EXPAND` layout for other aspect ratios is a change in one place.
- All input uses **pointer events** (mouse and touch alike). Buttons meet a 64 px minimum hit
  target, and hover is never required: hover only adds the tooltip and glow.
- **Planned for touch:** a tap-to-highlight / tap-again-to-use pattern for hotspots, plus larger
  dialogue choices.

### 4.8 Accessibility

- **Reduced motion**: defaults to the OS preference. It removes camera shake, softens flashes into
  fades and limits zoom.
- **Flicker:** the glitch flicker stays below 3 flashes per second in every mode.
- **Pacing:** cutscenes are skippable, and text speed is adjustable (0 = instant).
- **Text:** all on-screen text is live text, never baked into images. This keeps it crisp and
  translatable.

### 4.9 Rendering note

`render.maxTextures` is set to **1**. With Phaser's multi-texture batching enabled, animated rig
parts lost triangles in testing (seen in Chromium's software renderer; not yet ruled out on
hardware). Single-texture batches have no measurable cost at our sprite counts. Once rig parts are
packed into texture atlases (roadmap) we will re-test with `?maxtex=-1` on real GPUs.

## 5. Working with the code

```bash
npm install
npm run dev          # builds assets, starts Vite at http://localhost:5173
npm test             # unit tests
npm run typecheck
npm run build        # production build in dist/
npm run assets:validate   # check art deliveries only (exit code 1 on errors)
npm run rig:template      # regenerate docs/rig-template/ from player.rig.json
npm run rig:fit-walk -- --write   # refit walk bob + speed after changing leg joints
npm run smoke        # headless run of every scene + screenshots (needs Playwright + Chromium)
```

## 6. Roadmap after the prototype

1. **Rig test review.** First the art arrives in `assets-src/characters/player/`. Next we review
   it in the Rig Lab. Then we adjust rig proportions or joints if needed (`player.rig.json` →
   regenerate the template).
2. **Character creation scene.** This adds hair, outfit and skin choices, recoloured in code with
   a gradient-map filter, and name entry through the HTML overlay.
3. **Gus.** Once his design is approved, he becomes either a second rig or illustrated pose sets.
   His current placeholder is deliberately neutral.
4. **Texture atlases and WebP output** in the asset pipeline, plus per-scene loading.
5. **Audio manager**, with music, SFX and ducking under dialogue.
6. **Backend** (Node + Fastify + PostgreSQL): accounts or SSO, cloud saves, progress across the five
   districts, server-side answer checking, analytics.
7. **The five district games** (not started, by design).
